## 실패/조건부 항목 상세

### 항목 9: 구조 — 4단계 구조 준수

- **현재 상태**: 4단계 구조 자체는 갖추었으나, 섹션 번호가 `4.1 ~ 4.5`로 구성되어 있고 마지막 섹션이 `## 4.5 정리하며`임. chapter-structure.md의 마무리 규칙("각 장의 마지막 섹션 제목은 반드시 '정리하며'로 통일")은 충족함.
- **기대 상태**: 4단계 구조(도입→개념→실습→정리하며)를 명확히 구분하여 진행. 실제로 도입(스토리+핵심질문), 개념(스키마/CRUD/MCP), 실습(각 섹션 내 코드 실행), 정리하며 순서로 작성되어 구조적으로 정상.
- **판정 이유**: 구조 자체는 PASS이나, 섹션 번호가 5개(4.1~4.5)로 TOC와 다소 불일치하여 CONDITIONAL로 분류.

### 항목 10: 구조 — TOC.md 섹션 구조와 일치 여부

- **현재 상태**: TOC.md CH04 섹션은 다음 5개로 정의됨.
  - 섹션 1. 도입 (1p)
  - 섹션 2. 사내 시스템 확보 및 인프라 실행 (2p)
  - 섹션 3. 데이터베이스 스키마 분석 (3p)
  - 섹션 4. CRUD API 구조 이해 (2p)
  - 섹션 5. MCP(Model Context Protocol) 개념 소개 (2p)
  - 섹션 6. 정리하며 (0p → 섹션 5에 통합 명시)

  원고의 섹션 구성:
  - `## 4.1 사내 시스템 git clone으로 확보` (도입과 합침, 스토리 도입 포함)
  - `## 4.2 데이터베이스 스키마 분석`
  - `## 4.3 CRUD API 구조 이해`
  - `## 4.4 MCP(Model Context Protocol) 개념 소개`
  - `## 4.5 정리하며`

- **불일치 사항**:
  1. TOC.md에서 "도입(1p)"은 독립 섹션으로 명시되어 있으나, 원고는 도입 장면을 `4.1` 섹션 앞에 헤더 없는 본문으로 삽입하고 `## 4.1`이 "사내 시스템 git clone으로 확보"로 시작하여 TOC의 섹션 2와 맞지 않음.
  2. TOC에서 섹션 6("정리하며")은 "섹션 5에 통합"으로 명시되어 있으나, 원고는 `## 4.5 정리하며`를 독립 섹션으로 작성. 이는 실제 내용 품질을 높이는 방향이므로 긍정적이나 TOC와 구조적 불일치가 존재.
  3. TOC의 chapter_spec에서 섹션명 "사내 시스템 확보 및 인프라 실행" vs 원고 `4.1 사내 시스템 git clone으로 확보`로 표현 차이 존재.

- **기대 상태**: 원고 섹션 제목이 TOC.md에 명시된 섹션 제목 및 번호 체계와 일치하거나, 의도적 변경 사유가 있어야 함.
- **수정 제안**:
  - 방법 A: 도입부를 `## 4.0 도입` 또는 `## 4.1 도입`으로 명시하고 나머지 섹션을 `4.2 ~ 4.6`으로 재번호 부여.
  - 방법 B: 현재 섹션 번호 유지 시 TOC.md의 섹션 번호 체계를 원고에 맞게 정렬(허용 범위 내에서).
  - 중요도: TOC와의 섹션 제목 표현 차이는 경미한 수준이며, 내용 자체는 chapter_spec의 의도에 충실하게 작성되어 있음.

### 항목 14: 분량 — TOC.md 명시 10p와 실제 분량

- **현재 상태**: 원고 줄 수 기준 약 545줄. 마크다운 기술서 기준 A4 1페이지 = 약 40~50줄로 환산 시 약 11~14페이지에 해당. TOC 명시 분량 10p 대비 최대 +40% 초과 가능성 있음.
- **기대 상태**: ±20% 이내, 즉 8p~12p.
- **판정 이유**: 코드 블록, 출력 예시, Mermaid 다이어그램 등을 포함하면 실제 조판 시 10~12p 수준으로 수렴할 가능성이 높음. 텍스트 밀도가 높아 CONDITIONAL로 분류. 필수 항목이 아닌 권장 항목이므로 판정에는 영향을 주지 않음.
