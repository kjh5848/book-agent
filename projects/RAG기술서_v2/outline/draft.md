# 초안: AI 업무 비서 구축 — RAG + MCP 실전 가이드 (스토리텔링 버전)

## 기본 정보

- **책 제목**: AI 업무 비서 구축 — RAG + MCP 실전 가이드
- **부제**: 사내 문서와 DB를 LLM과 연결하는 지식 엔진 설계 전 과정
- **대상 독자**: Python 기초는 알지만 LLM/RAG는 처음인 초급 개발자
- **예상 분량**: 100페이지 이하
- **이론 vs 실습 비율**: 이론 30% / 실습 70%
- **집필 컨셉**: storytelling
- **집필 컨셉 설명**: 가상 팀이 실제 업무 문제를 해결해 나가는 서사 구조로 독자가 자연스럽게 기술을 체득한다

## 스토리 설정

### 주인공 팀 (story_persona)

**팀명**: "AI팀 팀원들" — 스타트업 HRTech 기업 "커넥트HR" 소속

| 이름 | 역할 | 특징 |
|------|------|------|
| **김도현** (팀장, 35세) | 백엔드 개발자 | Python 5년 경력, AI는 처음. 실용적 결정을 내린다 |
| **이서연** (개발자, 28세) | Python 2년 경력 초급 개발자 | 독자의 분신. 궁금한 것을 직접 묻는다 |
| **박민준** (데이터팀, 32세) | SQL 전문가 | DB 지식은 풍부하나 LLM은 낯설다 |

### 배경 상황

"커넥트HR"는 200개 기업의 HR 시스템을 관리하는 SaaS 스타트업이다.
매월 수백 건의 고객 문의가 들어오며, 팀원들은 사내 매뉴얼 3,000페이지를 뒤지며 답변을 작성한다.
이서연은 주당 10시간을 이 작업에 소비하고 있다.

팀장 김도현의 미션: "연말까지 고객 문의 응답 시간을 10분에서 30초로 줄여라."

## 챕터별 구성

### 1장. 이 책의 목표와 최종 완성본 미리보기 (프롤로그)

**이서연의 상황**: 팀 전체 회의에서 김 팀장이 3개월 목표를 발표한다. "응답 시간 30초 이내." 이서연은 처음 듣는 기술 용어들 앞에 얼어붙는다.

- 1.1 이 책이 다루는 범위 (Fine-tuning이 아닌 RAG 파이프라인)
- 1.2 최종 결과물 데모 시나리오 (정형+비정형 복합 질의응답)
- 1.3 전체 아키텍처 한 장 요약
- 1.4 사용 기술 스택 상세
- 1.5 이 책을 마치면 할 수 있는 것

### 2장. DeepSeek-R1으로 시작하는 기초 RAG 정복

**이서연의 상황**: "LLM한테 그냥 물어보면 되지 않나요?" — 처음 시도하는 날, 시스템이 환각을 일으키고 잘못된 연차 규정을 알려준다. 박민준 과장이 데이터를 직접 제공하는 방법을 제안한다.

- 2.1 [실패] LLM 단독 질의의 한계 (환각 체감)
- 2.2 [반쪽 성공] 프롬프트 직접 주입 (Context Injection)
- 2.3 [성공] VectorDB와 RAG의 시작 (ChromaDB + 검색)
- 2.4 [심화] DeepSeek-R1 추론(Reasoning) 활용

### 3장. 개발 환경 구축

**이서연의 상황**: 설치부터 난관이다. PostgreSQL 버전 충돌, Ollama 모델 다운로드 실패, 가상환경 꼬임. 김 팀장이 공통 설치 스크립트를 만들어 팀에 배포하기로 한다.

- 3.1 Ollama 설치 및 DeepSeek R1 모델 다운로드
- 3.2 PostgreSQL 설치 및 초기 설정
- 3.3 Python 3.11 가상환경 및 패키지 설치
- 3.4 환경 변수(.env) 구성 및 LLM Provider 스위칭 설계

### 4장. 베이스 시스템 확보

**이서연의 상황**: 회사 DB에 어떤 데이터가 있는지조차 모른다. 박민준 과장에게 "DB 구조 좀 알려줄 수 있어요?"라고 처음 부탁한다. 두 사람이 함께 스키마를 분석한다.

- 4.1 사내 시스템(직원·휴가·매출 DB) git clone으로 확보
- 4.2 데이터베이스 스키마 분석
- 4.3 CRUD API 구조 이해
- 4.4 MCP(Model Context Protocol) 개념 소개

### 5장. 사내 문서 표준화

**이서연의 상황**: 3,000페이지 PDF를 보고 절망한다. "이걸 다 어떻게 처리해요?" 김 팀장이 핵심 문서 50개를 먼저 선별하자고 한다. 작은 것부터 시작하는 전략.

- 5.1 RAG 검색 품질을 결정하는 문서 기준
- 5.2 PDF, Word, Markdown 수집 전략
- 5.3 문서 전처리 및 정규화 가이드라인
- 5.4 문서 버전 관리 및 메타데이터 설계

### 6장. 벡터 DB 구축

**이서연의 상황**: 처음으로 ChromaDB에 문서를 넣고 검색 결과를 확인하는 날. "세상에, 진짜 찾아오네요!" 처음으로 성취감을 느낀다.

- 6.1 텍스트 추출 (PyMuPDF, pdfplumber)
- 6.2 청킹(Chunking) 전략 — Fixed-size vs Semantic
- 6.3 임베딩 모델 선택 및 적용
- 6.4 ChromaDB에 저장 및 컬렉션 관리

### 7장. RAG Q&A 엔진 구현

**이서연의 상황**: 팀 내부 데모 날. 연차 규정을 묻자 정확한 출처와 함께 답변이 나온다. 박민준 과장이 처음으로 "이건 쓸 만하겠는데"라고 말한다.

- 7.1 LangChain RAG 파이프라인 설계
- 7.2 유사도 검색 및 컨텍스트 구성
- 7.3 출처 표시(Source Citation) 시스템
- 7.4 기본 채팅 인터페이스 연결

### 8장. 통합 에이전트 설계 (MCP + RAG)

**이서연의 상황**: 고객이 "김철수 씨의 이번 달 남은 연차는?"이라고 묻는다. DB도 뒤지고, 문서도 검색해야 한다. 두 세계를 연결하는 도전이 시작된다.

- 8.1 정형/비정형 분리 원칙
- 8.2 질문 라우팅 전략 (규칙 기반 → LLM 판단)
- 8.3 통합 응답 전략 (DB 조회 + 문서 검색 + LLM 합성)
- 8.4 대표 질문 시나리오 10개 실습

### 9장. LangChain 최종 연결

**이서연의 상황**: 개발 버전을 팀 내부에서 쓰다 보니 가끔 튕기고, 느리고, 로그도 없다. 김 팀장이 "이제 제대로 만들어보자"고 한다. 프로덕션 수준의 연결 작업.

- 9.1 Router / Agent / RAG Chain / MCP Tool 구성
- 9.2 MCP Tool 설계 (get_leave_balance, get_sales_sum 등)
- 9.3 운영 설정 (Timeout, Retry, 로깅, 캐싱)
- 9.4 비용 관리 및 토큰 모니터링

### 10장. RAG 시스템 튜닝

**이서연의 상황**: 내부 테스트에서 정확도 72%. "왜 이 질문에는 엉뚱한 답이 나오지?" 30개 테스트 케이스를 만들고 체계적으로 개선한다. 3개월 후 팀은 목표를 달성한다.

- 10.1 증상별 튜닝 가이드 (환각, 근거 부족, 엉뚱한 문서)
- 10.2 Chunk/Retriever 튜닝 (Semantic Chunk, k값, Metadata Filtering)
- 10.3 고급 기술 (ReRanker, Hybrid Search, Parent Document Retriever)
- 10.4 프롬프트 튜닝 (근거 우선, 모르면 모른다)
- 10.5 PDF 이미지 처리 (LLaVA + EasyOCR 하이브리드)
- 10.6 평가 체계 구축 (테스트셋 30개, Retrieval 정확도, Hallucination Rate)

## 실습 방식 (핵심 설계 원칙)

### AI 코드 실습 — GitHub Clone 후 실행

모든 챕터의 예제 코드는 GitHub 저장소에 완성본으로 준비합니다.
독자는 코드를 타이핑하거나 복사·붙여넣기하지 않고, `git clone` 후 즉시 실행합니다.

```
git clone https://github.com/{repo}/CH06_vector-db
cd CH06_vector-db
cp .env.example .env   # API 키 등 환경 변수만 직접 입력
pip install -r requirements.txt
python src/main.py
```

PostgreSQL, FastAPI CRUD 서버, 샘플 데이터 등 인프라는 별도 인프라 레포를 제공합니다.

```
git clone https://github.com/{repo}/rag-infra
cd rag-infra
docker-compose up -d
```
